01 · EXECUTIVE SUMMARY Antes y después en una página

De manual y riesgoso a declarativo y trazable

El cambio en una frase

Cada query EF declara membresía de tenant a través de HasQueryFilter que se nutre de ITenantContext; los controllers ya no necesitan acordarse de pasar companyId en cada llamada. Los IDs migran a Guid 7 para locality en el B-tree de Postgres.

Comparativa high-level

Antes
Tenant membership implícita y repetida

Cada repo escribía c.CompanyId == companyId a mano. Cada service recibía companyId como parámetro. Cada controller lo extraía del JWT. Tres lugares donde se podía romper el aislamiento.

→
Después
Tenant membership declarativa y única

EF Core aplica el filtro solo desde ITenantContext. Services y controllers no necesitan acordarse. Los 3 bugs cross-tenant quedan arquitectónicamente cerrados.

Antes
Identidad int autoincremental

IDs predecibles, fragmentación en B-tree de Postgres, riesgo de enumeración. Claim companyId inconsistente entre services.

→
Después
Guid 7 con timestamp

Primeros 48 bits = timestamp ms → locality en B-tree. Claim companyId en formato N (32 hex chars), constante única en Claims.cs.

Antes
Logs sin contexto de tenant

Cruzar un error en producción con su tenant era manual. Sin CompanyId en el log context, no había forma de correlacionar.

→
Después
Cada log lleva CompanyId

TenantLoggingMiddleware hace LogContext.PushProperty post-auth. Cross-tenant tracing = un grep.

02 · DIAGNÓSTICO Estado inicial auditado

El problema: estado inicial

Audit completo hecho en Cycle 1.0 antes de tocar una sola línea de producción.

Hallazgos cuantitativos

12 entities con int Id
AccountingTransaction, Category, Client, Company, Employee, Product, Purchase, PurchaseItem, Sale, SaleItem, Supplier, User. IDs predecibles, riesgo de enumeración, fragmentación en B-tree.
38 predicados manuales
c.CompanyId == companyId repetidos en cada repo. DashboardRepository solo tenía 17 de esos. Olvidar uno = tenant leak silencioso.
companyId en request DTOs
5 DTOs exponían CompanyId (CreateSaleRequest, CreateCategoryRequest, CreateProductDto, CreateUserDto, SupplierCreateDto). Cliente-controlled = disaster waiting.
3 bugs reales de cross-tenant leak
SalesController.Create ignora JWT. SupplierService.Create y Update usan request.CompanyId. Detalle en página siguiente.
Duplicación de fuentes de verdad
GetCurrentUserCompanyId() existía en BaseController y CurrentUserService. El literal "companyId" repetido en 3 lugares (controller, service, JwtService).
Boilerplate defensivo (~30 sitios)
Ensure(companyId != Guid.Empty, ...) en 10 services. Era código defensivo contra un bug que no podía ocurrir si el controller lanzaba 401 antes.
int.Parse(claim?.Value ?? "0")
Falla silenciosa con 0. Sin claim → companyId=0 → query devuelve todo. No era 401, era "todo el mundo es tenant 0".
CurrentUserService implementado pero bypassed
Existía pero ningún controller lo usaba. Path recomendado: eliminarlo + consolidar en HttpTenantContext.

El riesgo real

Riesgo: cualquier nuevo developer que tocara un repo y olvidara el predicado CompanyId == companyId creaba un tenant leak silencioso. No había ninguna capa arquitectónica que lo previniera — solo convenciones y code review.

03 · BUGS ENCONTRADOS Tres tenant leaks reales

Los 3 bugs cross-tenant

Descubiertos en auditoría de Cycle 1.0. Todos cerrados con regression tests en Cycle 1.1.

Bug #1 — SalesController.Create ignora JWT

Volterp.Api/Controllers/SalesController.cs · CreateSale (líneas 71-79) CRÍTICO 
// ANTES — nunca llamaba GetCurrentUserCompanyId()
public async Task<IActionResult> CreateSale([FromBody] CreateSaleRequest request)
{
    var sale = await _saleService.CreateSaleAsync(request);  // ❌ companyId nunca viaja

}

Impacto: una venta quedaba asociada al CompanyId del body. Un usuario de la Compañía A podía crear ventas para la Compañía B con solo editar el body.

Bug #2 — SupplierService.Create usa request.CompanyId

Volterp.Application/Services/SupplierService.cs · CreateSupplierAsync (líneas 31-54) CRÍTICO 
// ANTES — confiaba en el cliente
public async Task<SupplierDto> CreateSupplierAsync(SupplierCreateDto request)
{
    var supplier = new Supplier
    {
        Name = request.Name,
        CompanyId = request.CompanyId,  // ❌ viene del body
        // ...
    };
}

Impacto: proveedor de la Compañía B podía quedar registrado bajo la Compañía A (o viceversa). Cross-tenant data corruption silenciosa.

Bug #3 — SupplierService.Update reasigna CompanyId

Volterp.Application/Services/SupplierService.cs · UpdateSupplierAsync (línea 75) CRÍTICO 
// ANTES — el update pisaba el tenant
public async Task UpdateSupplierAsync(Guid id, SupplierUpdateDto request)
{
    var supplier = await _repo.GetByIdAsync(id);
    supplier.Name = request.Name;
    supplier.CompanyId = request.CompanyId;  // ❌ reasignación
    // ...
}

Impacto: aunque el supplier ya tuviera un CompanyId legítimo, el update lo sobrescribía con lo que mandara el body.

Patrón común: los 3 bugs vienen de confiar en datos cliente-controlled para algo que tiene que venir del JWT. La solución arquitectónica es mover la fuente de verdad del tenant a una sola capa.

05 · ARQUITECTURA OBJETIVO La visión antes de codear

La arquitectura objetivo

Decisiones arquitectónicas cerradas ANTES de empezar a codear.

Domain-centric
ITenantScoped en Domain (declara membresía). ITenantContext en Application (interface). EF en Infrastructure aplica HasQueryFilter. Domain no depende de EF ni de HTTP.
Guid 7 (no Guid 4)
Guid.CreateVersion7(): timestamp en los primeros 48 bits → locality en B-tree de Postgres → menos page splits que UUIDv4. Formato N (32 hex chars) en JWT claims.
Greenfield migration
DROP SCHEMA public CASCADE; CREATE SCHEMA public; + dotnet ef database update. Seeders usan Guid 7 con valores fijos (tests deterministas).
3 tenant contexts
HTTP (JWT, throw 401 si falta). Admin Global (cross-tenant, deferred). Tests/Seeder (NullTenantContext).
Wire refactor
companyId fuera de los request DTOs. Solo LoginResponse lo conserva (la UI lo necesita).
Whitelist cerrada de IgnoreQueryFilters()
Solo permitido para admin paths wrapped en IsSuperAdminOnly(). Por defecto, las queries siempre están filtradas.

El flujo de datos — antes vs después

Antes: tenant membership esparcida
Controller:  jwt.companyId → variable local
Service:     variable local → pasa como parámetro
Repository:  WHERE CompanyId == parámetro  (38 sitios)
EF:          ejecuta la query
Después: tenant membership centralizada
Controller:  jwt.companyId → ITenantContext (singleton scoped)
Service:     (no necesita companyId — EF lo lee solo)
Repository:  (no filtra — EF aplica HasQueryFilter)
EF:          lee ITenantContext.CompanyId → WHERE automático
Resultado: services y repositories dejan de tener la responsabilidad de filtrar. Es imposible olvidarse del filtro porque vive en una sola capa (el OnModelCreating del DbContext).

El truco del reflection en OnModelCreating

En lugar de editar las 12 EF Configurations para agregar HasQueryFilter una por una, el DbContext recorre las entities vía reflection y aplica el filtro automáticamente a las que tienen Guid CompanyId:

// Volterp.Infrastructure/Data/VolterpDbContext.cs (núcleo)
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    base.OnModelCreating(modelBuilder);

    foreach (var entityType in modelBuilder.Model.GetEntityTypes())
    {
        if (typeof(ITenantScoped).IsAssignableFrom(entityType.ClrType))
        {
            var method = typeof(VolterpDbContext)
                .GetMethod(nameof(ApplyTenantFilter), BindingFlags.NonPublic | BindingFlags.Instance)!
                .MakeGenericMethod(entityType.ClrType);

            method.Invoke(this, new object[] { modelBuilder });
        }
    }

    modelBuilder.Entity<Company>().HasQueryFilter(e => false); // bypass total
}

private void ApplyTenantFilter<TEntity>(ModelBuilder modelBuilder)
    where TEntity : class, ITenantScoped
{
    modelBuilder.Entity<TEntity>().HasQueryFilter(
        e => _tenantContext.CompanyId == null
          || EF.Property<Guid>(e, "CompanyId") == _tenantContext.CompanyId);
}

¿Por qué field-access y no closure-local?

Lección crítica: EF Core inlinea las closure-locals como SQL constants al model-build time. Si capturás var tenant = _tenantContext.CompanyId en una lambda, el filtro se lockea al primer valor visto (típicamente null durante EnsureCreated fuera de HTTP) → todas las queries unfiltered.

El fix: referenciar _tenantContext.CompanyId directamente en la lambda (field access). EF Core parameteriza el field access por query → filtro dinámico correcto.

10 · CYCLE 1.2 Guid 7 migration (a / b / c)

Cycle 1.2: migración a Guid 7

3 commits cohesivos · d5eac9e → bf55432 → 187b069

¿Por qué Guid 7 y no Guid 4?

Guid 4 (random)
Distribución uniforme → fragmentación en B-tree → page splits frecuentes en Postgres → write amplification.
Guid 7 (timestamp-based)
Primeros 48 bits = timestamp ms → IDs ordenables cronológicamente → locality en B-tree → menos page splits. Monotonicidad intra-millisecond en .NET 10.

Lecciones aprendidas

Gotchas que pueden morderte

PitfallPor qué muerdeFix
Closure-local en HasQueryFilter EF Core inlinea closure-locals como SQL constants al model-build time. El filtro se lockea al primer valor visto (típicamente null durante EnsureCreated fuera de HTTP). Todas las queries unfiltered. Referenciar _tenantContext.CompanyId directamente en la lambda. EF Core parameteriza el field access por query.
WebApplicationFactory vs runtime real Los integration tests con factory arman un scope que resuelve constructor injection sin quejarse. Pero en el runtime real, los middlewares se construyen una vez al startup desde el root provider. Probar la app de verdad, no solo los tests. El factory no reemplaza al startup real.
int.Parse(... ?? "0") Silent data corruption. Sin claim → companyId=0 → query devuelve todo. No es 401, es "todo el mundo es tenant 0". Siempre Guid.TryParse + throw UnauthorizedException en missing/malformed.
IgnoreQueryFilters() fuera de admin Bypassea el aislamiento. Si lo necesitás, estás haciendo admin work. Wrap en IsSuperAdminOnly() + whitelist cerrada.
Migrar a Guid 7 sin split Entre 1.2a y 1.2b el código no compila (~176 errors esperados). Si metés todo en 1 commit, el reviewer ve un delta inmanejable. Split en 3 commits cohesivos (a/b/c). Cada commit = unidad revisable.
Trust request.CompanyId Datos cliente-controlled. Un usuario de la Compañía A puede crear datos para la Compañía B con solo editar el body. companyId SIEMPRE del JWT, nunca del request.
